# d402 client for Python

A minimal agent-side implementation of [`spec/SPEC.md`](../../spec/SPEC.md) sections 2-7.2:
discover an offer, earn a voucher by labelling a bundle, and spend it through a
`requests` wrapper that handles the 402 handshake for you.

Dependencies: Python 3.10+, `cryptography`, `requests`. No build step.

## Install

Either copy the `d402/` folder next to your code, or:

```sh
cd clients/python && pip install -e .     # gives you `import d402` and the `d402` command
```

## Usage

```python
from d402 import D402Client, Keypair, lookup_solver, llm_solver

keypair = Keypair.load_or_create("~/.d402/keypair.json")          # Ed25519, created on first run (0600)
solver = llm_solver(lambda prompt: my_llm(prompt))                # or lookup_solver({"i_1": "tech", ...})
client = D402Client(keypair, solver=solver, model="claude", cache_path="~/.d402")

res = client.fetch("http://localhost:8787/search?q=gpu")          # 402 -> earn (get bundle, solve, sign, submit) -> retry
print(res.status_code, res.headers["D402-Calls-Remaining"], res.json())

res = client.fetch("http://localhost:8787/search?q=ceasefire")    # cached voucher, no earning
for v in client.status():
    print(v.sellerId, v.jti, v.calls, "calls left")
```

`fetch(url, method="GET", **requests_kwargs)` returns a plain `requests.Response`. Lower-level
pieces are there too: `discover(base)`, `get_bundle(task_url, tier)`, `submit(task_url, bundle, answers)`,
`earn(accept, tier=None)`, and the signing helpers `sign_submit`, `sign_spend`, `canonical_json`.
Protocol failures raise `D402Error(code, message, status, body)`; an ordinary non-2xx from the
gated route is just returned.

## Command line

```sh
export D402_HOME=~/.d402                               # default; holds keypair.json and vouchers.json
python -m d402 keygen                                  # prints the public key
python -m d402 discover http://localhost:8787
python -m d402 earn http://localhost:8787 --tier s --answers answers.json   # answers.json: {"i_1": "tech", ...}
python -m d402 fetch "http://localhost:8787/search?q=gpu"
python -m d402 status
```

`earn` and `fetch` take `--answers` (a lookup file) because the CLI has no LLM; in code you pass
`llm_solver`.

## Shared identity and cache with the TypeScript client

The file formats are identical to `@d402/client`, so both clients can run as the same agent:

- `keypair.json` is `{"publicKey", "privateKey"}` with base64url raw 32-byte keys, the file
  `loadOrCreateKeypair(path)` reads and writes.
- `cache_path` pointing at a directory uses `<dir>/vouchers.json`, the file `FileVoucherCache(dir)`
  uses: `{"version": 1, "vouchers": [{jti, sellerId, token, scope, calls, expiresAt, sub, taskUrl}]}`.
  Writes are atomic (temp file + rename) and the file is re-read on every operation, so a voucher
  earned from Python is spent from TypeScript and vice versa. `D402_HOME` is the same convention
  the d402 MCP server uses.

`canonical_json` is `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`
and is byte-identical to the TS `canonicalJSON` for strings, ints, bools, null, lists and objects
(the test suite checks both signatures against vectors generated by the TS implementation).

Bound spends (SPEC 7.1) are signed by default (`sign_spends=True`) and carry the SPEC 7.2
`D402-Nonce` (`spend_nonce=True`), the same as the TS client; sellers that do not bind vouchers
ignore the extra headers. `sign_spend(..., nonce=None)` gives the 5-line form for a seller that
predates 7.2.

## Tests

```sh
cd clients/python && python3 -m unittest -v          # or: python3 -m pytest -q
```

The integration tests start `examples/search-proxy` as a subprocess (needs `node` and the repo's
`node_modules`); they are skipped when the repo is not there.
